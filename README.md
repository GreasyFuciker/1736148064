# Microsoft Rewards 自动助手

Bing 搜索奖励助手用户脚本（Tampermonkey / Violentmonkey）。

> ⚠️ 自动化 Microsoft Rewards 可能违反其服务条款，存在积分作废或账号被封的风险。请自行判断是否使用。

## 安装

安装 Tampermonkey 后，新建脚本并粘贴 `microsoft-rewards-helper.user.js` 的内容，或直接拖入浏览器。

## 它做什么

1. 在 bing.com 右下角注入一个悬浮面板（可拖动、可折叠、跟随 Bing 的深浅色主题）。
2. 按设定的**检索次数**（默认 40 次）执行，跑满即停；能读到积分侧栏时顺带显示今日积分和每日任务状态，读不到也不影响主流程。
3. 以「起点 → 顺着相关搜索走几步 → 换个不相关的起点重新开始」的方式挑选搜索词；起点来自起始话题池、Bing 热搜与联想词，最近几天用过的词都不再重复。
4. 循环执行：搜索 → 在结果页滚动几秒 → 新标签页打开首条结果并在那边滚动 → 关掉它回到结果页停留 → 读奖励面板 → 随机间隔 → 下一次搜索，直到跑满设定的检索次数或手动停止。

## 原脚本（v1）的工作原理与问题

原脚本的整体思路是对的，但有几处结构性缺陷会让它实际上跑不出预期效果。

### 1. 搜索之后的整条流程从未执行（最严重）

v1 的 `performNextSearch()` 是这样串起来的：

```js
if (performSearch(term)) {          // 内部调用 searchForm.submit()，页面立刻开始跳转
    setTimeout(() => {
        simulateScrolling(() => {   // 滚动
            checkProgress(() => {   // 查进度
                waitForNextSearch();// 等待
            });
        });
    }, 2000);
}
```

表单提交触发导航，旧页面的 JS 上下文连同所有 `setTimeout` 一起被销毁。挂在后面的滚动、查进度、等待**一次都不会跑**。新页面加载后 `restoreState()` 接手，直接又发起下一次搜索。

结果：没有滚动、没有停留、没有间隔，搜索一个接一个地打出去——这恰恰是最容易被判定为异常的行为模式。

### 2. 已用搜索词在每次跳转后被清空

```js
function restoreState() {
    usedSearchTerms = new Set(savedState.usedSearchTerms || []);  // 恢复
    ...
    startSearchProcess();          // 而它第一行就是 usedSearchTerms.clear()
}
```

恢复出来的去重集合立刻被清掉，于是同一个词会被反复搜索。Bing 对重复查询不计分，进度自然涨不动。

### 3. 进度读不到时会立刻报"任务已完成"

```js
const remainingSearches = currentProgress.total - currentProgress.current;  // 0 - 0 = 0
if (remainingSearches <= 0 || currentProgress.completed) { /* 停止 */ }
```

`total` 初始为 `0`。只要侧栏数据没读到，一按开始就会显示"搜索任务已完成"然后停下。

### 4. 网络拦截过于宽泛，会误判进度

```js
const progressTextMatch = text.match(/(\d+)\/(\d+)/);
if (current <= total && total <= 100) { /* 当作进度 */ }
```

这条正则会命中站内**任意**响应里的任意 `数字/数字`——日期 `10/25`、比例、版本号都算。而且 v1 对每一个 fetch 都做 `clone().text()`，包括几百 KB 的搜索结果响应。

### 5. 侧栏 iframe 定位错误

`document.querySelector('iframe')` 取的是页面上第一个 iframe，在 Bing 上通常是广告或埋点框架，而不是奖励侧栏。

### 6. `openRewardsSidebar()` 的兜底分支写错了

```js
allLinks.forEach(link => {
    if (...) { link.click(); return true; }   // return 的是回调，不是外层函数
});
return false;                                  // 永远走到这里
```

`return true` 只是结束了当前回调，函数照样返回 `false`；同时循环不会中断，页面上**每一个** rewards 链接都会被点一遍。

### 7. 其他

- 新版卡片的自动点击用 `card.closest('.promo_cont')?.querySelector('a[href][target="_blank"]')` 取链接，容器里的第一个 `<a>` 会被所有卡片重复点中，点的永远是同一个任务。
- `config.waitTime`（等待时间）有配置项、能保存、能读取，但代码里**从来没有被使用过**。
- `searchInterval` 只在代码里存在，界面上无处可调。
- 进度行 `12/90` 实际是积分数而非搜索次数，却被当成次数用来算"还需搜几次"。
- `saveState()` 用 2 秒防抖写入，而搜索会立即跳转——最关键的那次写入经常丢失。
- `startCountdown` 用 `setInterval(1000)` 自减，长时间休息会明显漂移；且倒计时不跨页面。
- `domCache['rewards-progress'].textContent` 等处没有空值保护。
- 主题 `MutationObserver` 每次属性变动都全量重刷样式，没有防抖。

## v2 做了什么

### 架构：把状态机建在页面跳转之上

v2 承认"一次搜索 = 一次页面跳转"这个事实，把搜索定为一轮循环的**终点**而不是起点：

```
页面加载 → 恢复会话 → 滚结果页 → 浏览首条结果(新标签页) → 停留 → 读奖励面板 → (必要时休息) → 随机间隔 → 搜索(跳转)
   ↑                                                                                                  │
   └──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

当前阶段和它的**截止时间戳**一起写进 `localStorage`。刷新或跳转打断了休息？下次加载会接着把剩余时间等完，而不是从头再等 5 分钟。

### 逐条修复

| 问题 | v2 的处理 |
|---|---|
| 跳转后流程中断 | 循环重构为页面加载驱动，浏览/停留/读面板全部在新页面上执行 |
| 已用词被清空 | `restore()` 只恢复不重置，跨跳转保留去重集合 |
| 进度未知即判完成 | 引入 `progress.known`；未知时不判完成，改由「每日搜索上限」兜底终止 |
| 拦截误判 | 按 URL 白名单 `REWARDS_URL_RE` 过滤，只认 `pointProgress`/`current`+`total` 这类具名字段 |
| iframe 找错 | 按 `src` 含 `rewards|flyout` 定位，再按内容特征 `#bingRewards` 兜底 |
| `forEach` 里 return | 改用 `find()`，命中即返回，不再连点所有链接 |
| 卡片点错链接 | 改用 `card.closest('a[href]')`，并按 href 去重、每日只点一次、单轮最多 3 个 |
| `waitTime` 未使用 | 作为「停留时间」真正接入循环，滚动后停留让 Bing 记账 |
| 积分/次数混淆 | 干脆不再读积分，进度就是「已检索 N / 目标 M 次」（见下文） |
| 防抖丢状态 | 跳转前同步写入；轮询用不落盘的 `sleep()`，避免高频写 |
| 倒计时漂移 | 改为 250ms 采样 + 时间戳差值，长休息也准确 |

### 新增

- **每日搜索上限**（默认 60 次）——即使进度完全读不到，也不会无限循环。
- **搜索间隔可调**，默认放宽到 12–25 秒随机（v1 是 5–10 秒）。
- **各阶段时长随机浮动**（默认 ±30%），滚动节奏也不再是固定 1000ms 的节拍。
- **跨天自动重置**已用词与已点卡片；会话超过 45 分钟无活动自动作废。
- **停止即中断**：`stop()` 递增 `runToken`，正在 `await` 的阶段自行退出，不留悬空定时器。
- 直接 `location.assign('/search?q=...')` 发起搜索，比填充 `#sb_form_q` 再提交表单更可靠，也自动适配 `cn.bing.com`。
- 面板拖动限制在视口内，不会被拖出屏幕。

### 代码层面

- 引入 `el()` DOM 构造器，`createUI()` 从约 300 行缩到约 150 行。
- 所有 DOM 访问经 `$()` / `setText()`，带空值与失效缓存保护。
- 用括号配对解析 `flyoutViewModel` 的 JSON，会跳过字符串内的花括号（v1 的朴素计数遇到含 `{` 的查询词会截错）。
- 主题监听加 200ms 防抖。

## 配置项

面板里点「⚙️ 配置参数」展开，改动即时保存：

| 项 | 默认 | 说明 |
|---|---|---|
| 休息时间 | 5 分钟 | 每次休息的时长 |
| 浏览时长 | 10 秒 | 在打开的首条结果页里滚动浏览多久（退回原地滚动时也是这个值）|
| 结果页滚动 | 20 秒 | 打开首条结果**之前**先在结果页上滚多久，0 表示不滚 |
| 结果页浮动 | 70% | 结果页滚动这一段单独的 ±浮动幅度（20 秒 ±70% → 6~34 秒） |
| 停留时间 | 8 秒 | 关掉结果页回到搜索页后的静止停留，给 Bing 记账留出时间 |
| 休息间隔 | 12 次 | 每检索多少次休息一轮，设为 0 表示不休息 |
| 间隔下限 / 上限 | 12 / 25 秒 | 两次搜索之间的随机间隔 |
| 检索次数 | 40 次 | 每天搜多少次，达到即停。这是唯一的终止条件 |
| 随机幅度 | 30% | 浏览/停留/休息时长的 ±浮动幅度，设为 0 关闭随机 |
| 话题步数下限 / 上限 | 5 / 8 步 | 一个话题连续走几步后跳到新话题 |
| 起始话题 | 24 个英文话题 | 每行一个，可自由编辑（换成中文也行）；至少保留 2 个 |
| 不重复天数 | 3 天 | 最近几天用过的词不再重复，0 表示只按天去重 |
| 纳入 Bing 热搜词 | 开 | 起始话题用完后，用 Bing 首页热搜补充词库 |
| 用联想词扩充词库 | 开 | 用 Bing 联想接口补充词库 |
| 新标签页打开首条结果 | 开 | 关掉就退回旧行为：留在结果页原地滚动 |
| 自动点击奖励卡片 | 开 | 自动点开未完成的每日任务卡片 |

### 关于升级

话题列表存在 localStorage 里。从 v2.0 升上来时，如果你**没有改动过**自带的中文默认
列表，它会自动换成新的英文列表；只要你在面板里编辑过（哪怕只删了一行），就按你的
列表来，升级不会覆盖。

## 搜索之后：在新标签页里浏览首条结果

v2.4.0 之前，一次搜索之后的「模拟浏览」就是在结果页上下滚几下。真人不是这样用搜索
引擎的——搜出来是要点进去看的。现在的流程是：

```
搜索(跳转) → 在结果页滚动几秒 → 找到首条自然结果 → 新标签页打开 → 在那一页滚动 N 秒
          → 关掉它、焦点回到结果页 → 停留 → 读奖励面板 → 下一次搜索
```

结果页自己的滚动没有被替换掉，只是挪到了点进去之前——真人也是先扫几眼结果再点。
两段时长分开配置：「结果页滚动」管前半段，「浏览时长」管落地页那一段。

几个实现上的要点：

- **首条结果**从 `#b_results li.b_algo` 的标题链接一路放宽到「结果区里的第一条外链」，
  广告块（`.b_ad` 等）和站内入口（图片/视频/相关搜索）都排除。碰上 Bing 的点击跳转
  `/ck/a`，会把编码在 `u=a1<base64url>` 里的真实地址解出来直接打开：少一次跳转，
  URL 上的标记也不会在跳转里被吃掉。解不出来就原样打开那条 `/ck/a`。
- **怎么开这个标签页**：优先用脚本管理器的 `GM_openInTab`。标签页由扩展打开，
  **绕得过浏览器的弹窗拦截器**——`window.open` 不是点击触发的，默认会被直接挡掉，
  这正是 v2.4.0 装到浏览器里之后「一直在结果页滚动、从不开新标签页」的原因。
  没有这个 API 时才退回 `window.open`（那条路需要用户放行弹窗）。
- **谁来关这个标签页**：打开时把「浏览到什么时候」的时间戳写进 URL 的 hash
  （`#brhVisit=<时间戳>`），结果页上的脚本读到它就知道自己是被打开的，滚到点自己
  `window.close()`。但扩展开出来的标签页在 Chrome 里**不许**自己关（「脚本只能关闭
  自己打开的窗口」），所以真正负责收尾的是主标签页：过了截止时间再等 2 秒就
  `close()` 掉它。哪怕对方页面根本没跑起脚本（PDF、被跳转吃掉了 hash），流程也不会卡住。
- **标记还是丢了怎么办**（v2.6.0 修的就是这个）：跳转把 hash 吃掉、而
  `GM_openInTab` 开出来的标签页又没有 `window.opener`，两条老兜底就都够不着它了——
  表现正是「新标签页开出来了，但一下都不滚」。现在主标签页在开标签页**之前**先往
  GM 存储里写一张**访问票据**（`{host, deadline, createdAt}`）：GM 存储是按脚本存的，
  跨域也读得到，落地页认领这张票据就知道自己该滚到什么时候。票据有三道锁——
  只能认领一次、20 秒内有效、而且必须「跟票据上是同一个站」或「从 Bing 跳过来」，
  免得误关用户自己开的标签页。落地页滚完还会在票据上记一笔，主标签页看到就立刻收尾，
  不用干等宽限时间。
  `window.open` 那条路上仍然保留原来的 `postMessage` 握手（那种标签页有 opener）。
- **落地页滚不动怎么办**：不少站点把滚动条放在自己的容器上，document 根本不滚，
  这种页面上 `window.scrollBy` 调了也白调。所以滚动时会确认位置真的变了，连着两次
  没动就改滚页面里最大的那个可滚动容器。另外落地页加载太慢、拿到标记时截止时间已经
  过了的话，也至少浏览 3 秒再关——开了个标签页却一下没滚就关掉，跟没打开一样。
- **`@grant` 不再是 `none`**：要用 `GM_openInTab` 就得声明它，脚本因此跑进了
  脚本管理器的沙箱——沙箱里的 `window` 是一层代理，`window.fetch = ...` 只会改到代理上，
  页面里的 fetch 毫发无损。所以凡是要碰页面本身的地方（拦截 fetch/XHR、开标签页、
  收发 postMessage、判断自己在不在 iframe 里）都改用 `unsafeWindow`，脚本里叫
  `pageWindow`。拿不到 `unsafeWindow` 时自动退回 `window`，行为和以前一致。
- **@match 放开到了 `*://*/*`**：要在结果页里滚动、关闭，脚本就得在那一页上运行。
  但除访问模式外的一切（面板、搜索循环、网络拦截）只在 `www.bing.com` / `cn.bing.com`
  上启用，其余站点确认自己不是被脚本打开的之后立刻返回，不注入面板也不碰页面。
  Bing 的 `/ck/a` 中转页同样被排除在主流程之外，免得在那里再开一份面板、跑第二个循环。

### 没开新标签页时怎么排查

面板上的状态行会直接写明原因，两种情况：

| 面板显示 | 含义 | 怎么办 |
|---|---|---|
| `新标签页被拦截（请允许本站弹出窗口），改为在结果页滚动 N 秒` | 用的是 `window.open` 且被拦截器挡了 | 给 bing.com 放行弹出窗口（Chrome/Edge：地址栏右侧的拦截图标 → 始终允许）；正常情况下不该走到这条路，说明脚本管理器没提供 `GM_openInTab` |
| `没找到可打开的搜索结果，改为在结果页滚动 N 秒` | 结果页版式不认识 | 控制台里会打出 `#b_results` 里有多少条目、多少链接和前 5 个 href，照着补选择器即可 |
| `没有可用的搜索词，已停止` | v2.7.0 之前的老问题，三十来次就会撞上 | 升级到 v2.7.0；升级后这条几乎不可能再出现（组合词不依赖网络） |
| `结果页没跑起脚本，本次只打开没滚动` | 新标签页开出来了，但那一页上脚本没跑起来（站点限制、或者是 PDF 之类） | 该站点确实用不了就算了，不影响计数；如果**每一条**都这样，检查脚本管理器是不是限制了脚本只在 bing.com 运行 |

（v2.4.0 有个坑：这两条提示写进状态行之后，立刻被下一句「模拟浏览：滚动页面…」
盖掉了，用户只看得到在滚动，看不出为什么。现在原因和滚动提示合成一句，不会再被覆盖。）

控制台里每次加载都会打一行 `已加载 v2.7.0（开标签页方式: GM_openInTab）`，可以据此确认
脚本版本装对了没有、走的是哪条路。面板标题下面也一直显示版本号。

要彻底用回旧行为，在配置面板里关掉「新标签页打开首条结果」即可。

## 搜索词是怎么选的

搜索词不是一份固定清单，而是**每天都不同的随机游走**：

```
起点 coffee roast levels → 顺着结果页的相关搜索走 5~8 步 → 换到 World War II timeline 重新起步 → ...
```

**中间几步**取自当前结果页的相关搜索，每搜一次重新抓一次，所以路径随当天的页面内容
而变；走满掷出的步数（默认 5~8 步）就换一个不相关的起点重新开始——不换的话，从
coffee 出发走 30 步大概率还在咖啡圈里打转，一整天的搜索全落在一个话题簇里，这比
时间间隔更容易被看出来。

### 起点按这个顺序找，前一个空了才用后一个

| 来源 | 从哪儿来 | 说明 |
|---|---|---|
| **起始话题** | 配置面板里的话题池 | 24 个彼此不相关的英文话题，可自由编辑（换成中文也行） |
| **热搜词** | `bing.com/hp/api/model` | Bing 首页数据里的检索链接，就是当天的热词；接口不给就退回页面上的热搜/右栏模块 |
| **联想词** | `bing.com/osjson.aspx` | Bing 自己的联想接口，返回的是真人常搜的词，每次拿 3 个话题去问 |
| **组合词** | 本地拼的 | 「话题 + 后缀」（24 × 14 = 336 个组合），完全不依赖网络，永远不会枯竭 |

两个网络来源都是 **bing.com 同源**接口，不需要额外权限、不碰第三方站点，请求带 5 秒
超时，失败就静默跳过；连续 3 轮取不到词（接口改版、断网、被墙都算）就不再请求，
后面一路用组合词兜着，不会每轮白发请求。可以在配置面板里单独关掉「纳入 Bing 热搜词」
和「用联想词扩充词库」。

### 去重：三层

1. `usedTerms` —— 当天搜过的词一律不再搜，跨页面跳转持久化，跨天自动清空。
2. **跨天历史** —— 最近 `historyDays` 天（默认 3 天）用过的词都不再用，存在
   localStorage 里（最多 600 条，过期自动清理）。没有这一层的话，每天都从同一份
   起始话题池开工，第二天搜的还是那批词。设为 0 就退回「只按天去重」。
3. `tooSimilar()` —— 挡掉「换汤不换药」的连续搜索。仅靠字符串相等拦不住
   coffee → coffee beans → best coffee beans，所以额外排除互相包含、以及用字
   重合度 ≥ 80% 的词（只回看最近 6 个词，不影响隔得远的正常复现）。

### v2.7.0 之前：搜到三十来次就停

面板会显示「没有可用的搜索词，已停止」。原因是取相关搜索的选择器只认三种旧版式
（`.b_vList.b_divsec` / `.rslist` / `.richrsrailsuggestion_text`），而现在的 Bing 结果页
用的是 `.b_rs` 那一套——于是**几乎每一页都抓不到词**，随机游走每一步都得消耗一个新的
起始话题，24 个话题用完（外加零星几个抓到的词）正好三十来次，然后 `nextTopic()` 返回
null，`pickTerm()` 跟着返回 null，整个流程停机。

两处都修了：取词选择器改成「已知版式全收一遍取并集」，并且允许从链接的 `q` 参数里取词
（顺带过滤掉翻页、图片/视频入口这类噪声）；起始话题用完也不再是死路，后面还有热搜词、
联想词和组合词三级兜底。

## 为什么以“检索次数”为准，而不是积分进度

面板上的进度就是 `检索: 12/40 次`，不再显示积分。

早期版本把积分进度当作终止条件，于是只要侧栏读不到（跨域 iframe、Bing 改版导致
选择器失效、或者压根没打开积分面板），进度就是「未知」，整个流程也就无从判断该
不该停；更麻烦的是读**错**——把某个数字当成「已拿满」，一按开始就收工。

现在积分进度干脆不读了，终止条件只有一个：搜够设定的次数。侧栏只用来显示每日任务
状态和补充搜索词，读不到完全不影响主流程；连续 3 次读不到就不再每轮白等 6 秒轮询
（实测每轮从 10 秒降到 4 秒）。休息也一样，改成「每检索 N 次歇一轮」，不再依赖
「这轮涨没涨分」这种读数。

## 关于首页

脚本**不会**在页面加载时点击任何东西。这一点很重要：Bing 首页的积分入口是普通导航
链接，而搜索结果页的同名元素才是打开侧栏浮层的按钮。早期版本在空闲时也会去点它，
在首页上就变成「点击 → 跳转 → 脚本重载 → 再点击」的无限刷新（表现为地址栏停在
`bing.com/?form=RWSE01` 不停刷新，即使从未点过「开始搜索」）。

现在有三层防护：

1. 空闲时只做被动读取，不点击任何元素；侧栏没打开就显示「点开积分面板可显示每日任务」。
2. 真要点的时候，先判断该元素是否位于一个会导致跳转的 `<a href>` 里，是就跳过。
3. 刷新循环检测：脚本自己发起的跳转会打标记，30 秒内出现 3 次以上**非脚本发起**的
   加载即判定异常，立刻停掉全部自动操作并在面板上告警。手动点「开始搜索」可解除。

## 时间随机化

固定的节律本身就是机器特征，所以脚本里所有与时间相关的量都是随机的：

| 时机 | 随机方式 |
|---|---|
| 两次搜索之间 | 在「间隔下限 ~ 上限」内均匀取值（默认 12–25 秒） |
| 结果页滚动时长 | 基准值 ± **单独的**随机幅度（默认 20 秒 ±70% → 6–34 秒） |
| 浏览首条结果的时长 | 基准值 ± 随机幅度（默认 10 秒 ±30% → 7–13 秒） |
| 浏览结束后的停留 | 基准值 ± 随机幅度（默认 8 秒 ±30% → 6–10 秒） |
| 休息 | 基准值 ± 随机幅度（默认 5 分钟 ±30% → 3.5–6.5 分钟） |
| 每次滚动的间隔 | 600–1600ms 随机，首次滚动前还有 300–1000ms 的随机延迟 |
| 每次滚动的距离 | 100–400px 随机 |
| 滚动方向 | 70% 向下、30% 向上 |
| 搜索词挑选 | 从未使用过的词里随机取 |

把「随机幅度」设为 0 可以关掉时长浮动（搜索间隔仍然随机，因为它本来就是一个区间）。

## 验证

v2.2.0 时用 Playwright + Chromium 对着模拟的 Bing 页面（含同源侧栏 iframe、新旧两种
任务卡片、相关搜索区块）跑过端到端冒烟测试，确认：进度与进度条正确渲染、推广卡片被
正确排除、主页面与侧栏搜索词都能抓到、连续 4 次跳转使用了 4 个互不相同的搜索词、
全程无页面错误。

在真实 Chromium 里跑端到端测试（用 Playwright 的请求拦截把 `www.bing.com`、中转页和
落地页都换成本地模拟页，脚本按用户脚本的方式注入），五种情形分别验证：

| 情形 | 结果 |
|---|---|
| `window.open` 路径 | 打开首条自然结果（广告被跳过）、URL 带 `#brhVisit=`、落地页滚动、4 秒后自行关闭、主标签页接着搜下一个词 |
| `GM_openInTab` 路径（模拟扩展开标签页，页面无权自关） | 同上，由主标签页在截止时间后关掉，实测存活 6.0 秒 |
| **跳转把 hash 吃掉 + 没有 opener** | 落地页靠 GM 票据照样滚起来（scrollTop 193），随后被正常关闭——v2.5.0 在这一步就是「开了不滚」 |
| 落地页的滚动条在内部容器上（`body` 不滚） | 自动改滚容器，实测 scrollTop 124 |
| 弹窗被拦截（`window.open` 返回 null） | 面板说明原因、退回结果页滚动、2 次检索照常跑完 |

另有 38 条纯逻辑用例：hash 标记的写入与解析、过期时间戳被忽略、首条结果筛选挡掉
广告/站内链接/隐藏元素、`/ck/a` 不进主流程，以及票据的三道锁（只能认领一次、
超时作废、跨站且非 Bing 来源一律不认领）和 `/ck/a` 的 base64 解码。

真实 Bing 页面的版式没法在这里覆盖，第一次用的时候仍建议把检索次数调小（比如 3 次）
看一轮再放开。
